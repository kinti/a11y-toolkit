# Adding a language to a11y-toolkit

The engine's messages live in **locale packs** — plain JSON files, one per
language, editable from the GitHub web UI with no tooling installed:

```
a11y_toolkit/locales/
  en.json          ← reference (English)
  es.json          ← Español
  _template.json   ← copy me
```

A locale pack is community-editable by design: same model as axe-core's
`locales/`, plus mechanical validation axe-core doesn't have.

## Add your language in four steps

1. **Copy the template**: `cp a11y_toolkit/locales/_template.json a11y_toolkit/locales/<code>.json`
   (BCP-47 code: `fr`, `de`, `gl`, `ca`, `eu`, `pt-BR`…).
2. **Fill `_meta`**:
   ```json
   "_meta": {
     "name": "Galician", "native": "Galego",
     "plural": "n == 1", "dir": "ltr"
   }
   ```
   `plural` is a CLDR-style expression over `n` — `True` selects the `one`
   form. Most European languages: `n == 1`. `dir`: `ltr` or `rtl`.
3. **Translate every value**, keeping the `{placeholders}` (`{n}`, `{ej}`…)
   EXACTLY as they are — they are filled by the engine at runtime.
4. **Validate** (no install needed):

   ```bash
   python3 tests/test_locales.py
   ```

   The check is mechanical: same keys as English, same placeholders per
   message, a working plural rule, no empty values. If it is green, the PR is
   reviewable at a glance.

## What is covered

Every user-facing message: findings and their remediations (all 100+ signals),
limits and honesty notes, statement/VPAT legal wording, badge texts, CLI error
messages. What is NOT in packs (by design): the WCAG criterion *knowledge*
entries (`a11y_criterion` explanations — data, not messages) and code comments.

## How the runtime uses packs

- **Fallback chain**: a missing key falls back to English — a half-translated
  pack degrades gracefully, though the validation gate requires completeness
  to merge.
- **Plurals**: an entry may be `{"one": "1 pair", "other": "{n} pairs"}`;
  the locale's `plural` rule picks the form.
- **Overlays** (for downstream products): `a11yi18n.use_overlay(path)` layers
  a `{"<lang>": {"<namespace>": {...}}}` file on top — brand voice, custom
  wording — without forking the engine. The overlay always wins.

## Notes for reviewers

- A new locale PR should touch exactly one file: `locales/<code>.json`.
- `tests/test_locales.py` green = structurally sound. Reading a sample of the
  translations is the human part.
- Native-speaker review beats machine review; the test only guarantees the
  pack is *wired* correctly.
